K. Security Posture
- K1. **INJECTION PREVENTION**: Protection against injection attacks (command, code, variable, path injection):
  - **COMMAND INJECTION** (CRITICAL):
    - **FORBIDDEN**: `eval "${VAR}"` → NEVER use `eval` with variables or user input
    - **FORBIDDEN**: `command $VAR` (unquoted variable) → Command injection risk (see D3e)
    - **FORBIDDEN**: `$(eval "command ${VAR}")` → NEVER use `eval` in command substitutions
    - **FORBIDDEN**: `command "$(printf '%s' "${VAR}")"` when VAR contains command separators (`;`, `|`, `&`, `&&`, `||`)
    - **FORBIDDEN**: `command "${VAR}"` when VAR is user-controlled and contains shell metacharacters
    - **SAFE ALTERNATIVES**:
      - Never use `eval` → Use direct command execution or function calls
      - Always quote variables: `command "${VAR}"` (but validate VAR doesn't contain command separators)
      - Sanitize user input: Validate format before use, escape special characters
      - Use arrays for arguments: `command "${args[@]}"` (prevents injection in arrays)
      - Use `command -v` for command validation: `command -v "${cmd}"` before executing
    - **VALIDATION**: Find all `eval` usage: `grep -nE '\beval\s' script.sh` → Must be removed or documented as safe
    - **DETECTION**: Find unquoted variables in commands: `grep -nE 'command\s+\$[^{]' script.sh` → Must be quoted
    - **CROSS-REFERENCE**: See D3d (command substitution), D3e (word splitting) for related patterns
  - **VARIABLE INJECTION** (HIGH):
    - **FORBIDDEN**: Unquoted heredoc delimiters with user-controlled content (see E2)
    - **FORBIDDEN**: Unquoted variables in command contexts (see D3e)
    - **FORBIDDEN**: Variable expansion in eval/exec contexts
    - **VALIDATION**: Ensure all variables are quoted and validated before use
    - **CROSS-REFERENCE**: See E2 (heredoc quoting), D3e (word splitting), C1 (unbound variables)
  - **PATH INJECTION** (MEDIUM):
    - **FORBIDDEN**: `cd "${VAR}"` when VAR contains `..` or absolute paths (directory traversal)
    - **FORBIDDEN**: `cat "${VAR}"` when VAR contains `/etc/passwd` or other sensitive paths
    - **FORBIDDEN**: Unquoted path variables: `command $PATH_VAR` (pathname expansion risk)
    - **SAFE ALTERNATIVES**:
      - Validate paths before use: `[[ "${PATH}" =~ ^[a-zA-Z0-9_/.-]+$ ]]` (alphanumeric, slash, dash, dot, underscore only)
      - Use `realpath` to canonicalize paths: `real_path=$(realpath "${VAR}")`
      - Check path boundaries: Ensure path doesn't escape intended directory
      - Use `basename`/`dirname` to extract safe path components

    - **CROSS-REFERENCE**: See J1 (file existence validation), D3f (globbing)
  - **REGEX INJECTION** (MEDIUM):
    - **FORBIDDEN**: `grep -E "${USER_PATTERN}"` when PATTERN is user-controlled (regex injection)
    - **FORBIDDEN**: `sed -E "s/${USER_PATTERN}/replacement/"` when PATTERN is user-controlled
    - **SAFE ALTERNATIVES**:
      - Use `grep -F` for fixed-string matching when pattern is user-controlled

      - Escape regex special characters if regex is required: `printf '%s\n' "${PATTERN}" | sed 's/[][.*+?^${}()|\\]/\\&/g'`
    - **VALIDATION**: For user-controlled patterns, use `-F` flag or validate pattern format
    - **CROSS-REFERENCE**: See D3c (grep unsafe patterns)
  - **ARITHMETIC INJECTION** (LOW):
    - **FORBIDDEN**: `(( VAR + USER_INPUT ))` when USER_INPUT contains shell code
    - **FORBIDDEN**: `let "VAR = ${USER_INPUT}"` → Variable injection risk
    - **SAFE ALTERNATIVES**:
      - Validate input is numeric before arithmetic: `[[ "${INPUT}" =~ ^[0-9+-/*() ]+$ ]]`

  - Check CMakeCache.txt after configuration for incorrect detection (e.g., NO_LIBM=1 when libm is available)
  - Add pre-configuration CMake cache files to force correct settings before CMake runs
  - Verify linker flags contain required libraries: `CMAKE_SHARED_LINKER_FLAGS`, `CMAKE_EXE_LINKER_FLAGS`
  - Use `CMAKE_*_LINKER_FLAGS_INIT` to ensure flags apply to all targets from the start
  - Post-build verification: check built libraries with `ldd` to confirm required libraries are linked
- M8. **CMAKE FLAG DOCUMENTATION REQUIREMENT**: BEFORE compiling ANY library with CMake, verify comprehensive flag documentation exists:
  - **MANDATORY**: Documentation file MUST exist at `docs/flags/LIBRARY_VERSION_CMAKE_FLAGS_DOCUMENTATION.md`
  - **MANDATORY**: Documentation MUST include: library version, source repository, source commit hash, generation date, CMake minimum version
  - **MANDATORY**: ALL CMake flags used in build script MUST be documented with: flag type (OPTION/STRING/PATH/CACHE), default value, description, usage example
  - **MANDATORY**: Build script MUST include inline comment referencing the documentation file
  - **VALIDATION**: If documentation doesn't exist, WARN user and PROMPT to create it
  - **ERROR PREVENTION**: This check prevents using undocumented/invalid flags that are silently ignored by CMake
- M9. **CMAKE FLAG CROSS-REFERENCE VALIDATION**: For EVERY CMake flag used (-D FLAG=VALUE), verify against documentation:
  - **MANDATORY**: Each `-D FLAG=VALUE` in cmake command MUST be listed in corresponding docs/flags/*.md file
  - **MANDATORY**: Flag name MUST match exactly (case-sensitive) - e.g., `USE_CUDA` NOT `Ceres_ENABLE_CUDA`
  - **MANDATORY**: Flag type in script must match documented type (OPTION for ON/OFF, STRING for paths/values)
  - **COMMON ERRORS TO PREVENT**: Using prefix that doesn't exist, using old/deprecated flag names, using "assumed" flags that are never actually defined
- M10. **VERSION-SPECIFIC FLAG VALIDATION**: When upgrading library versions, verify all CMake flags are still valid:
  - **MANDATORY**: When changing library version, regenerate flag documentation for new version
  - **MANDATORY**: Compare old vs new flag documentation to identify deprecated/removed/renamed flags
  - **MANDATORY**: Update build script to use new flag names and remove deprecated flags
- M11. **CMAKE FLAG VALIDATION**: All CMake flags MUST be validated against official library documentation:
  - REQUIRED: Before adding CMake flags, verify against library's official documentation (e.g., docs/flags/CERES_SOLVER_2.2.0_CMAKE_FLAGS_DOCUMENTATION.md)
  - FORBIDDEN: Using undocumented or library-specific prefixed flags (e.g., `Ceres_ENABLE_CUDA` → use `USE_CUDA`)
  - FORBIDDEN: Passing framework-specific flags to libraries that don't support them (e.g., `MKL_ROOT` to Ceres)
  - REQUIRED: Use standard CMake variables (BLA_VENDOR, BLAS_LIBRARIES, LAPACK_LIBRARIES) for BLAS/LAPACK configuration
  - VALIDATION: Run `scripts/helpers/validate_cmake_flags.sh` on script before commit
- M12. **UNDOCUMENTED FLAG DETECTION AND VERIFICATION**: All CMake flags MUST be verified against documentation before use:
  - **MANDATORY**: When encountering ANY `-D FLAG=VALUE` in cmake command, check if flag exists in docs/flags/*.md file
  - **MANDATORY**: If flag is NOT documented, download library Git repository and parse CMakeLists.txt/cmake files to verify flag existence
  - **MANDATORY**: If flag exists in source but NOT in documentation, add it to documentation with proper type, description, and usage
  - **MANDATORY**: If flag does NOT exist in source, REMOVE it from build script (it's being silently ignored)
  - **DETECTION METHOD**: Search for `option(FLAG`, `set(FLAG`, `CACHE STRING "FLAG"`, `CACHE BOOL "FLAG"` in CMakeLists.txt and cmake/*.cmake files
  - **VERIFICATION SOURCES**: Library Git repository (primary), official documentation (secondary), wiki/forums (tertiary)
  - **COMMON EXAMPLES**: 
    - Ceres: `SUITESPARSE_INCLUDE_DIR`, `CHOLMOD_LIBRARY` → NOT valid (use `SuiteSparse_DIR` or `CMAKE_PREFIX_PATH`)
    - SuiteSparse: `METIS_LIBRARY_DIR` → NOT valid (METIS is bundled, not external)
  - **AUTO-FIX**: If undocumented flag is found, remove it from build script and use correct documented alternative
- M13. **HPC LIBRARY CONFLICT DETECTION**: When configuring HPC libraries (MKL, OpenBLAS, TBB), detect and prevent conflicts:
  - MKL/OpenBLAS conflict: NEVER link both MKL BLAS and OpenBLAS in same library
  - TBB conflict: Ensure system TBB is used, NOT MKL's bundled TBB (check `TBB_LIBRARIES` points to `/usr/lib/x86_64-linux-gnu/libtbb.so`, NOT `/opt/intel/*/tbb`)
  - BLAS vendor consistency: All libraries in dependency chain must use same BLAS (all MKL or all OpenBLAS)
  - Verification: After CMake configure, check `CMakeCache.txt` for mixed BLAS/TBB
  - Prevention: Always verify library paths after configuration, not just "found" status
- M14. **LIBRARY BUNDLED COMPONENT DETECTION**: Before linking external libraries, verify what's bundled vs what needs separate linking:
  - **CRITICAL**: Check library documentation and repository to identify bundled dependencies (e.g., SuiteSparse bundles METIS in newer versions)
  - **MANDATORY CHECKS**: Parse CMakeLists.txt for FetchContent_Declare/add_subdirectory, check CHANGELOG/RELEASES for "bundled"/"integrated" keywords, verify official docs, inspect installed library headers/binaries (`nm -D lib*.so | grep symbol`), cross-reference with pkg-config files
  - **VERSION AWARENESS**: Different versions may have different bundling strategies (e.g., SuiteSparse < 7.0 requires separate METIS, >= 7.1 bundles METIS)
  - **CHANGELOG ANALYSIS**: Use `git log v7.0.0..v7.1.0 --grep="METIS\|dependency\|bundle"` and `git diff` to check version transitions
  - **PROS/CONS**: Document decision rationale (bundled: simpler build, version compatibility vs larger binary; separate: shared libs, easier updates vs version mismatch risks)
  - **DETECTION PATTERNS**: Check for `add_subdirectory.*metis` in CMakeLists.txt, look for external/third_party directories, verify symbols with `nm -D`
  - **OFFICIAL SOURCE VERIFICATION**: Check library website, GitHub README, CMake config files, distribution package metadata, build system output
  - **DOCUMENTATION REQUIREMENT**: When integrating library, document in comments: library version, bundled components, separate components, source URL, verification date, decision rationale
  - **AUTOMATED ANALYSIS TOOL**: Use `prompts/Library-Analysis-Tool.md` to automate bundled component detection
- M-TOOLS: When analyzing library dependencies, CMake flags, or bundled components, consider using `prompts/Library-Analysis-Tool.md` for automated comprehensive analysis before manual verification.
  - **APT SOURCES FORMAT**: Support both legacy and modern apt sources formats (legacy: `/etc/apt/sources.list` and `*.list` files; modern: `*.sources` deb822 format for Ubuntu 24.04+). Parse both `deb http://...` lines AND `URIs: http://...` fields from .sources files. Update mirror URLs in BOTH formats when modifying apt sources.

O. Testing, Validation & Graceful Degradation
- O1. Built-in validation checks (self-tests, sanity checks) before performing irreversible actions.
- O2. Optional dry-run or verbose mode behavior reviewed for correctness and safety.
- O3. Documentation of manual verification steps when automation cannot fully guarantee success.
- O4. **MULTI-PHASE INSTALLATION VERIFICATION**: Library installation verification MUST use multiple independent checks with retry logic:
  - **MANDATORY PHASE 1 - File Existence**: Verify library file exists before checking caches (e.g., `[ -f "/usr/local/lib/libname.so" ]`)
  - **MANDATORY PHASE 2 - Linker Cache**: Check library appears in ldconfig cache (e.g., `ldconfig -p | grep "libname.so"`)
  - **MANDATORY PHASE 3 - Retry Logic**: If cache check fails, refresh ldconfig and retry verification
  - **MANDATORY PHASE 4 - Version Check**: Where applicable, verify library version matches expected (e.g., `pkg-config --modversion libname`)
  - **MANDATORY**: Detailed debug logging at each phase showing what was checked and why it passed/failed
  - **SINGLE-CHECK ANTI-PATTERN**: Do NOT rely solely on ldconfig cache check - files can exist but not be in cache (transient failures)
  - **ERROR HANDLING**: On failure, provide actionable debug output (file listing, cache contents, suggestions)
  - **RELIABILITY IMPROVEMENT**: Single-phase checks are ~70% reliable, multi-phase with retry are ~95% reliable
  - **PREVENTS**: False negatives from stale ldconfig cache, race conditions, transient filesystem issues
- O5. **SHELLCHECK VALIDATION & AUTO-CORRECTION**: All Bash scripts MUST be validated with ShellCheck and all errors/warnings MUST be corrected:
  - **MANDATORY**: Run ShellCheck on all `.sh` files before completing the audit: `shellcheck script.sh` or `shellcheck -x script.sh` (if script uses `source`)
  - **MANDATORY**: Fix ALL ShellCheck errors (exit code 1) - these indicate real issues that must be resolved
  - **MANDATORY**: Fix ALL ShellCheck warnings (exit code 0 with warnings) - warnings indicate potential issues or style violations
  - **AUTO-FIX CAPABILITY**: Use project's auto-fix script if available: `scripts/helpers/auto_fix_shellcheck.sh script.sh` to automatically fix common ShellCheck issues
  - **SHELLCHECK SEVERITY LEVELS**:
    - **ERROR (SC1xxx)**: Syntax errors, fatal issues - MUST be fixed immediately
    - **WARNING (SC2xxx)**: Style issues, portability concerns - MUST be fixed
    - **INFO (SC3xxx)**: Suggestions, best practices - SHOULD be addressed
    - **STYLE (SC4xxx)**: Code style recommendations - SHOULD be addressed
  - **COMMON SHELLCHECK ISSUES TO FIX**:
    - **SC2086**: Double quote to prevent globbing and word splitting → Fix: Quote variables: `"${VAR}"` instead of `${VAR}`
    - **SC2155**: Declare and assign separately to avoid masking return values → Fix: `local var; var=$(command)` instead of `local var=$(command)`
    - **SC1090**: Can't follow non-constant source → Fix: Use `# shellcheck source=path/to/file` directive or disable with `# shellcheck disable=SC1090`
    - **SC2001**: See if you can use `${variable//search/replace}` instead → Fix: Use parameter expansion when possible
    - **SC2046**: Quote this to prevent word splitting → Fix: Quote command substitution: `"$(command)"`
    - **SC2068**: Double quote array expansions → Fix: Quote array: `"${array[@]}"` instead of `${array[@]}`
    - **SC2181**: Check exit code directly with `if`, don't use `$?` → Fix: `if ! command; then` instead of `command; if [ $? -ne 0 ]; then`
    - **SC2034**: Variable appears unused → Fix: Remove unused variable or mark with `# shellcheck disable=SC2034` if intentionally unused
    - **SC2120**: Function name references arguments, but none are ever passed → Fix: Remove unused parameters or use `_` prefix
    - **SC2119**: Use `"$@"` if function's $1 should mean script's $1 → Fix: Use `"$@"` for forwarding arguments
  - **SHELLCHECK DIRECTIVES**: When ShellCheck warnings are false positives or intentional, use inline directives:
    - `# shellcheck disable=SC2086` - Disable specific warning for next line
    - `# shellcheck disable=SC2086,SC2155` - Disable multiple warnings
    - `# shellcheck source=path/to/file` - Tell ShellCheck where to find sourced file
    - `# shellcheck shell=bash` - Specify shell type if shebang is missing
