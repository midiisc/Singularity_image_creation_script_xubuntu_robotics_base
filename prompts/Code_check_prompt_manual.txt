A. Structure & Syntax
- A1. Shebang compatibility, POSIX/Bash feature alignment.
- A2. Syntax correctness, indentation, formatting, line wrapping.
- A3. Avoidance of deprecated or non-portable constructs unless justified.
- A4. Declaration order: functions and variables are defined before first use (or accompanied by guards) to avoid relying on implicit forward declarations.
- A5. Favor POSIX-safe command patterns; when Bash-specific constructs are required, document the justification and ensure degradations are gracefully handled.
- A6. **BASH VERSION COMPATIBILITY**: Check for Bash 4+ features that may not work in older versions:
  - FORBIDDEN: `${var^^}` (uppercase) - use `tr '[:lower:]' '[:upper:]'` instead
  - FORBIDDEN: `${var,,}` (lowercase) - use `tr '[:upper:]' '[:lower:]'` instead
  - FORBIDDEN: Associative arrays (`declare -A`) without version check
  - When using Bash 4+ features, add explicit version check: `if [ "${BASH_VERSINFO[0]}" -ge 4 ]; then ... else ... fi`

B. Shell Options & Execution Controls
- B1. Appropriate use/scope of `set -e`, `set -u`, `set -o pipefail`, `set -E`, `set -o errtrace`, and subshell guards.
- B2. Documentation of intentional relaxations (e.g., `set +e`, `|| true`) and local scoping for risky sections.

C. Variables & Defaults
- C1. Detection/handling of unbound variables with `${var:-default}` or `${var:?message}` as appropriate.
- C2. Correct use of `local`, `readonly`, `declare -r`, exported variables, and avoidance of unintended global state.
  - **CRITICAL**: NEVER use `local` keyword outside a function - this causes error "local: can only be used in a function"
  - Check every `local` declaration is inside a function body
  - For global variables, use plain assignment or `declare` (without `local`)
  - Suggested commands: `grep -n '^[[:space:]]*local ' script.sh` to find `local` declarations, verify each is inside a function
- C3. Safe handling of arrays, indexes, and `IFS` mutations (restore defaults after use).
- C4. Each variable is declared once, with an explicit, meaningful default or guard. Later redeclarations are removed in favor of the carried-forward definition, and usages reference the original declaration.
- C5. **UNBOUND VARIABLE PROTECTION**: When using `set -u` or expecting unbound variables, ensure all variables have defaults:
  - Use `${VAR:-default_value}` pattern consistently
  - For environment variables that may not be set: `CACHE_DIR="${CONTAINER_APT_CACHE:-/var/cache/apt/archives}"`
  - Export critical variables in profile scripts: `/etc/profile.d/*.sh` and `/etc/environment`
  - Add fallback detection logic for missing environment variables before first use

D. Quoting & Expansion Safety
- D1. Proper quoting/escaping for variables, command substitutions, arithmetic, glob patterns, and path generation.
- D2. Verification of `read` usage (`read -r`, IFS settings) and word-splitting safeguards.
- D3. **PIPE PATTERN SAFETY**: Avoid unsafe `echo | grep` patterns; prefer here-strings or direct grep on variables:
  - UNSAFE: `if echo "${VARIABLE}" | grep -q "pattern"; then` (creates unnecessary subshell, potential echo flag interpretation)
  - SAFE: `if grep -q "pattern" <<< "${VARIABLE}"; then` (here-string, no subshell, explicit quoting)
  - SAFE: `if [[ "${VARIABLE}" =~ pattern ]]; then` (Bash regex, no external command)
  - Detection: `grep -n 'echo.*|.*grep' script.sh` to find all occurrences
- D4. **SED CHARACTER CLASS ESCAPING**: Validate sed bracket expressions for correct escaping and error handling:
  - **CRITICAL**: Bracket expressions must escape brackets correctly: `[][]` for literal `[` or `]`
  - **CRITICAL**: All command substitutions with sed MUST have error fallback: `|| echo ""`
  - **COMMON ERRORS**: `sed 's/[[\/&]/\\&/g'` (malformed - should be `sed 's/[][\\\/&]/\\&/g' || echo ""`)
  - **BRACKET CLASS SYNTAX**: Use `[][]` to match literal `[` or `]`, `\\` for backslash, `\/` for forward slash
  - **ERROR FALLBACK**: When `set -u` is active, ALWAYS add `|| echo ""` to sed/awk/grep in command substitutions
  - **CONSISTENCY**: All similar escaping operations must use identical patterns
  - **DETECTION**: `grep -nE "sed 's/\[\[" script.sh` (malformed), `grep -nE '\$\(.*sed.*\)' script.sh | grep -v '|| echo'` (no fallback)
  - **REAL ERROR**: Line 945 used `sed 's/[[\/&]/\\&/g'` without fallback → script crashed with `set -u` → Fix: `sed 's/[][\\\/&]/\\&/g' || echo ""`

E. Here-docs & Here-strings
- E1. Use of quoted delimiters (`<<'EOF'`) where literal content is intended.
- E2. Assurance that heredocs do not leak variables unexpectedly or leave temp files.
- E3. Use of `<<-` when tab-stripping is needed and documented.

F. Logic & Flow Control
- F1. Correct conditional expressions (`[[` vs `[`], `(( ))`), loops, and arithmetic.
- F2. Correct treatment of exit codes (`$?`, `||/&&`, negated commands).
- F3. Safe handling of subshells, command groups, and background jobs (`wait`, exit check).

G. Functions & Modularization
- G1. Proper function definitions, parameter handling (`$@`, `$*`, shifts), defaulting, and return semantics.
- G2. Ensuring functions do not leak state (globals, directory changes, shell options).
- G3. Proper use of `trap` within functions and restoration of environment on exit.
- G4. Functions grouped logically; helper functions declared ahead of dependents or referenced safely via sourcing order checks.
- G5. Each function is defined exactly once before first use; if discovered later in the file, relocate the definition earlier and remove duplicates, updating references to match the retained definition.

H. Error Handling & Observability
- H1. Exit-status checks for all external commands and pipelines; logging of actionable error messages.
- H2. `trap` handlers clean up resources (temp files, mounts, jobs) and re-raise signals when appropriate.
- H3. Logging differentiates stdout/stderr where helpful; optional scoped `set -x` toggles documented.

I. Timeouts, Retries, & Robustness
- I1. Long-running operations (e.g., `ldconfig`, package managers, service checks) wrapped with `timeout`, retries, or backoff.
- I2. Graceful degradation/fallback behavior documented when timeouts or partial failures occur.
- I3. Handling of transient network or IO failures, including retries and validation of results.
- I4. **HTTP ERROR HANDLING**: All curl/wget operations must check HTTP status codes and handle errors:
  - Capture HTTP status codes: `curl -w "%{http_code}" -o output_file URL`
  - Check for HTTP errors: 403 (Forbidden/Blocked), 404 (Not Found), 5xx (Server Errors)
  - Detect connection errors: timeouts, connection refused, DNS failures
  - Implement fallback logic when primary source fails (e.g., fallback to archive.ubuntu.com for mirrors)
  - Use temporary files to capture both stdout and stderr separately for proper error analysis
  - Validate HTTP codes are 3-digit numbers before checking: `[[ "${http_code}" =~ ^[0-9]{3}$ ]]`
  - Always provide user-visible error messages explaining the specific failure (403, timeout, etc.)

J. Edge Cases & Resiliency
- J1. Input validation, file/directory existence checks, and permissions (`umask`) where relevant.
- J2. Safe temporary resource management (`mktemp`, secure paths).
- J3. Handling of empty/whitespace-only data, concurrency hazards, and race conditions.
  - Suggested pattern: wrap `read` loops with `while IFS= read -r line || [ -n "$line" ]; do ...; done`.

K. Security Posture
- K1. Protection against injection (no unsafe eval, sanitized inputs).
- K2. Safe path handling, avoidance of world-writable directories, deliberate permission settings.
- K3. Explicit management of file descriptors (e.g., `exec {fd}`) when opened manually.
  - Example: Replace `TMP_DIR=/tmp/foo` with `TMP_DIR=$(mktemp -d -t foo.XXXXXX)` and `trap 'rm -rf "${TMP_DIR}"' EXIT`.

L. Performance & Maintainability
- L1. Avoid needless subshells, command substitutions in tight loops, prefer built-ins (`printf` over `echo -e`).
- L2. Clear comments for intentional complexity, avoidance of duplicated logic.
- L3. Readability: consistent naming, structure, modularization, and comment density that explains non-trivial control flow. Refresh stale comments or insert concise summaries when logic evolves.
- L4. **DOCUMENTATION COVERAGE REQUIREMENT**: 
  - **MANDATORY**: Every function > 10 lines MUST have documentation comment before definition
  - **MANDATORY**: Complex logic blocks (multi-phase, nested conditionals, long loops) MUST have explanatory comments
  - **BEST PRACTICE**: Minimum 25% comment density in complex code sections
  - **REQUIRED**: Comments explain WHY (rationale, assumptions, edge cases), not WHAT (code is self-documenting)
  - **REQUIRED**: Update comments when code changes (stale comments are worse than no comments)
  - **AUTO-FIX**: Pre-commit hook automatically adds missing header documentation
  - **VALIDATION**: Documentation validator checks all code files before commit
- L5. **MULTI-PHASE LOGIC DOCUMENTATION**: Complex detection/configuration logic with multiple phases MUST be documented:
  - REQUIRED: Header comment explaining overall strategy and number of phases
  - REQUIRED: Phase markers (e.g., "# Phase 1: ...") before each distinct phase
  - REQUIRED: Final decision comment explaining how phases combine
  - Example pattern (3-phase SDK detection): Header comment → Phase 1 marker → Phase 2 marker → Phase 3 marker → Final decision comment
  - Rationale: Multi-phase logic is complex; without clear phase markers, maintainers cannot understand the detection strategy
- L5a. **CONTROL STRUCTURE MARKERS (REQUIRED)**: All control structures MUST have closing markers to track pairings:
  - **MANDATORY**: `if ... then` → `# ENDIF: <condition description>` comment before `fi`
  - **MANDATORY**: `for ... in` → `# ENDFOR: <loop variable>` comment before `done`
  - **MANDATORY**: `while ... do` → `# ENDWHILE: <condition description>` comment before `done`
  - **MANDATORY**: `case ... in` → `# ENDCASE: <case variable>` comment before `esac`
  - **PURPOSE**: Helps debug missing if-fi, for-done, while-done, case-esac pairings
  - **AUTO-FIX**: Pre-commit hook automatically adds missing markers
  - **VALIDATION**: Control structure marker validator checks all pairs
- L6. When documenting updates, call out the self-contained blocks you touched (e.g., loop, trap handler, function) and confirm their comments, whitespace, and readability were brought in line with project conventions.

M. Environment & Dependencies
- M1. Validation that required external commands/binaries exist (`command -v`, `hash`) and version-sensitive behavior is documented.
- M2. Verification of environment assumptions (shell, OS, distro, architecture, locale, `LANG`, `LC_ALL`, `PATH`, proxy settings).
- M3. Safe handling of configuration files, credentials, and secrets (no accidental logging, enforce permissions).
- M4. Package detection/checking uses resilient helpers (e.g., `dpkg_resolve_installed_package`, `dpkg_get_installed_version`) instead of brittle parsing of `dpkg -l` or similar command output; replace and verify during the audit.
- M5. Confirm installation logic never removes or downgrades distro-provided packages (especially Python runtimes) inadvertently; prefer `apt-get install --no-remove --ignore-hold` or equivalent safeguards, and document rationale when relaxations are necessary.
- M6. Ensure locally compiled or source-installed packages are guarded from subsequent package-manager overwrites by pinning (`/etc/apt/preferences.d`) or an equivalent industry-standard protection mechanism; verify pins are scoped, documented, and cleaned up when no longer required.
- M7. **CMAKE CONFIGURATION VALIDATION**: When building software with CMake, validate critical configuration options:
  - Check CMakeCache.txt after configuration for incorrect detection (e.g., NO_LIBM=1 when libm is available)
  - Add pre-configuration CMake cache files to force correct settings before CMake runs
  - Verify linker flags contain required libraries: `CMAKE_SHARED_LINKER_FLAGS`, `CMAKE_EXE_LINKER_FLAGS`
  - Use `CMAKE_*_LINKER_FLAGS_INIT` to ensure flags apply to all targets from the start
  - Post-build verification: check built libraries with `ldd` to confirm required libraries are linked
- M8. **CMAKE FLAG DOCUMENTATION REQUIREMENT**: BEFORE compiling ANY library with CMake, verify comprehensive flag documentation exists:
  - **MANDATORY**: Documentation file MUST exist at `docs/flags/LIBRARY_VERSION_CMAKE_FLAGS_DOCUMENTATION.md`
  - **MANDATORY**: Documentation MUST include: library version, source repository, source commit hash, generation date, CMake minimum version
  - **MANDATORY**: ALL CMake flags used in build script MUST be documented with: flag type (OPTION/STRING/PATH/CACHE), default value, description, usage example
  - **MANDATORY**: Build script MUST include inline comment referencing the documentation file
  - **VALIDATION**: If documentation doesn't exist, WARN user and PROMPT to create it
  - **ERROR PREVENTION**: This check prevents using undocumented/invalid flags that are silently ignored by CMake
- M9. **CMAKE FLAG CROSS-REFERENCE VALIDATION**: For EVERY CMake flag used (-D FLAG=VALUE), verify against documentation:
  - **MANDATORY**: Each `-D FLAG=VALUE` in cmake command MUST be listed in corresponding docs/flags/*.md file
  - **MANDATORY**: Flag name MUST match exactly (case-sensitive) - e.g., `USE_CUDA` NOT `Ceres_ENABLE_CUDA`
  - **MANDATORY**: Flag type in script must match documented type (OPTION for ON/OFF, STRING for paths/values)
  - **COMMON ERRORS TO PREVENT**: Using prefix that doesn't exist, using old/deprecated flag names, using "assumed" flags that are never actually defined
- M10. **VERSION-SPECIFIC FLAG VALIDATION**: When upgrading library versions, verify all CMake flags are still valid:
  - **MANDATORY**: When changing library version, regenerate flag documentation for new version
  - **MANDATORY**: Compare old vs new flag documentation to identify deprecated/removed/renamed flags
  - **MANDATORY**: Update build script to use new flag names and remove deprecated flags
- M11. **CMAKE FLAG VALIDATION**: All CMake flags MUST be validated against official library documentation:
  - REQUIRED: Before adding CMake flags, verify against library's official documentation (e.g., docs/flags/CERES_SOLVER_2.2.0_CMAKE_FLAGS_DOCUMENTATION.md)
  - FORBIDDEN: Using undocumented or library-specific prefixed flags (e.g., `Ceres_ENABLE_CUDA` → use `USE_CUDA`)
  - FORBIDDEN: Passing framework-specific flags to libraries that don't support them (e.g., `MKL_ROOT` to Ceres)
  - REQUIRED: Use standard CMake variables (BLA_VENDOR, BLAS_LIBRARIES, LAPACK_LIBRARIES) for BLAS/LAPACK configuration
  - VALIDATION: Run `scripts/helpers/validate_cmake_flags.sh` on script before commit
- M12. **HPC LIBRARY CONFLICT DETECTION**: When configuring HPC libraries (MKL, OpenBLAS, TBB), detect and prevent conflicts:
  - MKL/OpenBLAS conflict: NEVER link both MKL BLAS and OpenBLAS in same library
  - TBB conflict: Ensure system TBB is used, NOT MKL's bundled TBB (check `TBB_LIBRARIES` points to `/usr/lib/x86_64-linux-gnu/libtbb.so`, NOT `/opt/intel/*/tbb`)
  - BLAS vendor consistency: All libraries in dependency chain must use same BLAS (all MKL or all OpenBLAS)
  - Verification: After CMake configure, check `CMakeCache.txt` for mixed BLAS/TBB
  - Prevention: Always verify library paths after configuration, not just "found" status
- M13. **LIBRARY BUNDLED COMPONENT DETECTION**: Before linking external libraries, verify what's bundled vs what needs separate linking:
  - **CRITICAL**: Check library documentation and repository to identify bundled dependencies (e.g., SuiteSparse bundles METIS in newer versions)
  - **MANDATORY CHECKS**: Parse CMakeLists.txt for FetchContent_Declare/add_subdirectory, check CHANGELOG/RELEASES for "bundled"/"integrated" keywords, verify official docs, inspect installed library headers/binaries (`nm -D lib*.so | grep symbol`), cross-reference with pkg-config files
  - **VERSION AWARENESS**: Different versions may have different bundling strategies (e.g., SuiteSparse < 7.0 requires separate METIS, >= 7.1 bundles METIS)
  - **CHANGELOG ANALYSIS**: Use `git log v7.0.0..v7.1.0 --grep="METIS\|dependency\|bundle"` and `git diff` to check version transitions
  - **PROS/CONS**: Document decision rationale (bundled: simpler build, version compatibility vs larger binary; separate: shared libs, easier updates vs version mismatch risks)
  - **DETECTION PATTERNS**: Check for `add_subdirectory.*metis` in CMakeLists.txt, look for external/third_party directories, verify symbols with `nm -D`
  - **OFFICIAL SOURCE VERIFICATION**: Check library website, GitHub README, CMake config files, distribution package metadata, build system output
  - **DOCUMENTATION REQUIREMENT**: When integrating library, document in comments: library version, bundled components, separate components, source URL, verification date, decision rationale
  - **AUTOMATED ANALYSIS TOOL**: Use `prompts/Library-Analysis-Tool.md` to automate bundled component detection
- M-TOOLS: When analyzing library dependencies, CMake flags, or bundled components, consider using `prompts/Library-Analysis-Tool.md` for automated comprehensive analysis before manual verification.
  - **APT SOURCES FORMAT**: Support both legacy and modern apt sources formats (legacy: `/etc/apt/sources.list` and `*.list` files; modern: `*.sources` deb822 format for Ubuntu 24.04+). Parse both `deb http://...` lines AND `URIs: http://...` fields from .sources files. Update mirror URLs in BOTH formats when modifying apt sources.

O. Testing, Validation & Graceful Degradation
- O1. Built-in validation checks (self-tests, sanity checks) before performing irreversible actions.
- O2. Optional dry-run or verbose mode behavior reviewed for correctness and safety.
- O3. Documentation of manual verification steps when automation cannot fully guarantee success.
- O4. **MULTI-PHASE INSTALLATION VERIFICATION**: Library installation verification MUST use multiple independent checks with retry logic:
  - **MANDATORY PHASE 1 - File Existence**: Verify library file exists before checking caches (e.g., `[ -f "/usr/local/lib/libname.so" ]`)
  - **MANDATORY PHASE 2 - Linker Cache**: Check library appears in ldconfig cache (e.g., `ldconfig -p | grep "libname.so"`)
  - **MANDATORY PHASE 3 - Retry Logic**: If cache check fails, refresh ldconfig and retry verification
  - **MANDATORY PHASE 4 - Version Check**: Where applicable, verify library version matches expected (e.g., `pkg-config --modversion libname`)
  - **MANDATORY**: Detailed debug logging at each phase showing what was checked and why it passed/failed
  - **SINGLE-CHECK ANTI-PATTERN**: Do NOT rely solely on ldconfig cache check - files can exist but not be in cache (transient failures)
  - **ERROR HANDLING**: On failure, provide actionable debug output (file listing, cache contents, suggestions)
  - **RELIABILITY IMPROVEMENT**: Single-phase checks are ~70% reliable, multi-phase with retry are ~95% reliable
  - **PREVENTS**: False negatives from stale ldconfig cache, race conditions, transient filesystem issues
