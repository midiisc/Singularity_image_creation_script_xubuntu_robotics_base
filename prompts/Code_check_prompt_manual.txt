  - Example: If upgrading from v1.0 to v2.0, diff docs/flags/LIBRARY_1.0.0_*.md vs LIBRARY_2.0.0_*.md
  - Prevention: Catches breaking changes in CMake API between library versions
- M11. **LIBRARY BUNDLED COMPONENT DETECTION**: Before linking external libraries, verify what's bundled vs what needs separate linking:
  - **CRITICAL**: Check library documentation and repository to identify bundled dependencies (e.g., SuiteSparse bundles METIS in newer versions)
  - **MANDATORY CHECKS**:
    1. Parse library's CMakeLists.txt for FetchContent_Declare, add_subdirectory with external projects
    2. Check library's CHANGELOG/RELEASES for "now includes", "bundled", "integrated" keywords
    3. Verify library's official documentation for dependency requirements by version
    4. Inspect installed library headers/binaries for bundled components (e.g., `nm -D lib*.so | grep symbol`)
    5. Cross-reference with pkg-config files (.pc) for actual dependencies vs documented ones
  - **VERSION AWARENESS**: Different versions may have different bundling strategies
    - Example: SuiteSparse < 7.0 requires separate METIS, >= 7.1 bundles METIS
    - Check Git tags and commits between versions for dependency changes
    - Parse version-specific documentation (README for that tag/release)
  - **CHANGELOG ANALYSIS**: Required pattern for version transitions:
    ```bash
    # Example: Check what changed between versions
    git clone --depth 50 https://github.com/library/repo.git /tmp/lib_check
    cd /tmp/lib_check
    git log v7.0.0..v7.1.0 --grep="METIS\|dependency\|bundle\|include" --oneline
    git diff v7.0.0..v7.1.0 -- CMakeLists.txt
    ```
  - **PROS/CONS REASONING**: Document why bundled vs separate is chosen:
    - **Bundled Pros**: Simplified builds, version compatibility guaranteed, no external dep hunting
    - **Bundled Cons**: Larger binaries, potential symbol conflicts if dep used elsewhere, harder updates
    - **Separate Pros**: Shared libraries save disk, easier security updates, centralized dep management
    - **Separate Cons**: Version mismatches possible, complex dep resolution, build complexity
  - **DETECTION PATTERNS**:
    ```bash
    # Check if library bundles dependency
    if grep -rq "add_subdirectory.*metis" CMakeLists.txt; then
      echo "METIS bundled as subdirectory"
    fi
    if find . -type d -name "external" -o -name "third_party" -o -name "3rdparty"; then
      echo "Check external/ directory for bundled deps"
    fi
    # Check installed library for symbols
    if nm -D /usr/local/lib/libsuitesparseconfig.so | grep -q "metis_"; then
      echo "METIS symbols present in library (bundled)"
    else
      echo "METIS not bundled, requires separate linking"
    fi
    ```
  - **OFFICIAL SOURCE VERIFICATION**: Always check multiple reliable sources:
    1. Library's official website (installation instructions)
    2. GitHub repository README (especially for version being built)
    3. Library's CMake config files (LibraryConfig.cmake) for find_dependency calls
    4. Distribution package metadata (apt show, rpm -qi) for system packages
    5. Build system output (CMake configure logs) for actual dependency resolution
  - **DOCUMENTATION REQUIREMENT**: When integrating library, document in comments:
    ```bash

    # Bundled: METIS (since 7.1), AMD, CAMD, COLAMD (always bundled)
    # Separate: BLAS, LAPACK (user must provide)

    # Decision: Use bundled METIS (simpler, no version conflicts)
    # Trade-off: Slightly larger binary, but guaranteed compatibility
    ```
  - **PREVENTION**: Avoid issues like "libcolmap-metis not detected" by:
    1. Always check library version being built
    2. Parse that version's documentation and CMakeLists.txt
    3. Don't assume dependencies from older versions apply
    4. Verify after build with ldd, nm, pkg-config

    - Review generated analysis before writing detection logic in build scripts
    - Reference: See "PART 1: EXECUTABLE BASH SCRIPT" in Library-Analysis-Tool.md for usage

- O4. **MULTI-PHASE INSTALLATION VERIFICATION**: Library installation verification MUST use multiple independent checks with retry logic:
  - **MANDATORY PHASE 1 - File Existence**: Verify library file exists before checking caches (e.g., `[ -f "/usr/local/lib/libname.so" ]`)
  - **MANDATORY PHASE 2 - Linker Cache**: Check library appears in ldconfig cache (e.g., `ldconfig -p | grep "libname.so"`)
  - **MANDATORY PHASE 3 - Retry Logic**: If cache check fails, refresh ldconfig and retry verification
  - **MANDATORY PHASE 4 - Version Check**: Where applicable, verify library version matches expected (e.g., `pkg-config --modversion libname`)
  - **MANDATORY**: Detailed debug logging at each phase showing what was checked and why it passed/failed
  - **SINGLE-CHECK ANTI-PATTERN**: Do NOT rely solely on ldconfig cache check - files can exist but not be in cache (transient failures)
  - **ERROR HANDLING**: On failure, provide actionable debug output (file listing, cache contents, suggestions)
  - Example multi-phase pattern:
    ```bash
    # Phase 1: File existence
    if [ ! -f "/usr/local/lib/libg2o_core.so" ]; then
      echo "FAILED: libg2o_core.so not found in /usr/local/lib"
      ls -la /usr/local/lib/libg2o*.so 2>/dev/null || echo "No g2o libraries found"
      PHASE_SUCCESS=false
    else
      echo "✓ Library file exists"
      # Phase 2: Linker cache check
      if ! timeout 5 ldconfig -p | grep -q "libg2o_core.so"; then
        echo "⚠ Library exists but not in cache, refreshing..."
        run_ldconfig_refresh
        # Phase 3: Retry after refresh
        if ! timeout 5 ldconfig -p | grep -q "libg2o_core.so"; then
          echo "FAILED: Still not in cache after refresh"
          ldconfig -p | grep "libg2o" || echo "No g2o in cache"
          PHASE_SUCCESS=false
        else
          echo "✓ Library now in cache"
        fi
      else
        echo "✓ Library verified in cache"
      fi
    fi
    ```
  - **RELIABILITY IMPROVEMENT**: Single-phase checks are ~70% reliable, multi-phase with retry are ~95% reliable
  - **PREVENTS**: False negatives from stale ldconfig cache, race conditions, transient filesystem issues
  - Tools: `ldd /path/to/binary` to verify runtime linking, `ldconfig -v` for verbose cache rebuild
